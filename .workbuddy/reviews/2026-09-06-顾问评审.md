## 一、业务漏洞

### P0-1 · 信用额度是死数字，永不变化

- **证据**：`creditUsed` 全库只有 4 处读取（`order.create.ts:62`、`credit.check.ts:16/26`、
  `customer.query.ts:35`），**零处写入**；唯一写入点是 `prisma/seed.ts` 的初始值。
- **后果**：建单不占用、取消不释放、出货不核销。同一客户连下 10 单，第 11 单超额也照过。
- **连带**：`05_TEST_LOG` 第 6 条「信用额度超额 block ✅」是**假阳性** ——
  那次能触发只因种子里王五 `creditUsed=28000 / limit=30000` 已贴上限。
- **修法（选一，不要都做）**：建单即占用 / 确认时占用，二选一写进 `04_DECISIONS`；
  取消与变更原单时回冲。

### P0-2 · 一张订单永远只有一行

- **证据**：`order.create.ts:165 / 192` 都是单行 `create: [{...}]`；修订也是 `deleteMany + create` 单行。
- **后果**：「给张三来 100 个 A-100 和 200 个 B-200」第二行被静默丢弃，确认卡只显示一行。
  **这是"演示一深就穿帮"的典型场景。**
- **连带**：`delivery.create` 的 `order.items.length === 1` 分支当前恒为真，
  部分出货暂时正确 —— 但靠的是"单行"这个隐性约束兜底，不是设计。
  一旦支持多行，传 `qty` 会被**静默忽略并出全部剩余**（不报错），定时炸弹。

### P1-3 · 预留账本与出货互不相干

- **证据**：`delivery.confirm` 只 `qty -= item.qty`，**不动 `reserved`**；
  `inventory.reserve` 单独 +，`release` 单独 -。
- **后果**：预留 50 → 出货 50 → `qty` 减 50 而 `reserved` 仍 50 → 可用凭空少 50，须手工 release 才平。
- **且**：预留无任何字段指向订单 / 出货单，无法回答"这 50 个是给谁留的"。
- **建议**：PoC 阶段在 UI 明示"预留与出货是两套账，需手工释放"；
  或把 `inventory.reserve/release` 移出主演示路径。

### P1-4 · 个人用语表三个行为缺陷

| # | 缺陷 | 证据 | 违反 |
|---|---|---|---|
| a | **rejected 仍会被再提议** | `lexicon.ts:281 proposeFromConfirm` 不过滤 `status='rejected'` | 11 号文档验收第 3 条 |
| b | **"记住"是批量盲记** | `ConfirmCard.tsx:170-203` 一次点击 = 记整个 utterance 为 verb 用语 + 记**全部** customer/product 槽位，用户无选择权 | 设计意图 |
| c | **单字也会命中** | `lexicon.ts:57` `if (t.includes(q)) return 0.9 + 0.1*(q.length/t.length)`；q="张" t="张三" → 0.95 ≥ 阈值 | 11 号文档"仅 len≥2 才算模糊命中" |
| d | **读操作产生写副作用** | `touchHit` 每次命中 `hits++`，interpret 路径每槽位一次 | 缓存 / 只读场景不适用 |

(b) 的额外问题：整句 `phraseNorm` 极长，只有一字不差才可能命中，等于往词表塞垃圾。

### P1-5 · status 枚举缺两个值

- `order.query.json:28` enum = `[DRAFT, CONFIRMED, SHIPPED, CANCELLED]`，
  缺 `PARTIALLY_SHIPPED` / `SUPERSEDED`。
- `resolve.ts` enum_alias 校验 `meta.enum.includes(hit)` → 「查部分出货的单」直接判非法并弹候选。
  **刚做的部分出货，查询端没跟上。**
- ✅ 已核对无误：`order.cancel` 对 `PARTIALLY_SHIPPED` 会落到最后的兜底分支被拒，无漏洞。
