# 语音输入为主 · 端侧模型选型评估

> 出具：顾问评审 · 2026-09-07
> 场景：Agent ERP 类软件，语音输入为主 / 文字为辅，模型需打包进软件本体
> 目标机假设：**无独显的普通 Windows 笔记本（16GB RAM）**——若按独显机设计，分发面会窄一大截

---

## 零、结论先行

| 问题 | 结论 |
|---|---|
| 1.7B 是否必要 | **要，但不是常驻，且不该让它干全部活**。1.7B 是目前中文端侧的性价比甜点；但你的任务本质是「12 分类 + 槽位抽取」，不是生成。正确做法：LLM **只做动词分类（输出 3–5 个 token）**，槽位继续走规则 |
| 能否更小 | 能。分三层：规则/用语表 → 0.6B 分类 → 1.7B 生成兜底。实测你的规则基线已是 96%/98.3%，LLM 只需补最后 4% |
| ASR 选谁 | **sherpa-onnx + SenseVoice int8（229MB）**，配 Silero VAD 做「说完一句识别一句」。不是真流式，但对「说完执行」的 ERP 语义反而更准 |
| 最小体积 | 必装包 **≈240MB**（纯 ASR，不开 LLM 也能用）；1.7B 作**可选组件**首次用时下载，装完总计 ≈1.35GB |
| 许可红线 | 只有 **Apache 2.0** 的能闭源分发且无 UI 署名义务 → **Qwen3 / 星火 X2.5 / sherpa-onnx / SenseVoice** 可用；**GLM-Edge、MiniCPM 有强制署名条款，直接出局** |

## 一、关于「火星 1.6B/1.8B」的确认

先对齐名词：你说的很可能是 **讯飞星火 X2.5 系列**（讯飞 2023 年首发时叫「讯飞火星」，后改名星火）。2026-09-01 由科大讯飞全资子公司**词元星火（XHToken）**开源了两款端侧模型：

| 型号 | 参数 | 上下文 | 许可 | 关键数据 |
|---|---|---|---|---|
| Spark-X2.5-1.7B | 1.7B | **原生 1M token** | **Apache 2.0** | BF16 权重 ~3.4GB；4bit 量化后 ≈1.0–1.2GB；Domux 智能家居控制指令端到端正确率 **90.3%**，平均响应 **0.85s**；MCP-Atlas 23.4 分（同尺寸最高） |
| Spark-X2.5-4B | 4.1B | 原生 1M token | **Apache 2.0** | 4B 档，显存/内存翻倍 |

架构：混合注意力（1 层全注意力 + 3 层滑窗注意力），长文本显存只有传统全局注意力的 1/4。训练约 20 万亿 token，昇腾集群。兼容 vLLM / SGLang / llama.cpp / Ollama / LM Studio，支持 LLaMA-Factory 微调。

**对你的意义**：1M 上下文对你这个场景**基本没用**（一句话才 20 个 token），但 90.3% 的**指令执行正确率**和 0.85s 响应是实打实对口的——它就是在「语音说一句 → 设备执行动作」这个 benchmark 上刷的分。

## 二、Q1 · 1.7B 是否必要？能更小吗？

### 2.1 你的任务不是「生成」，是「分类 + 抽取」

Agent ERP 的链路是：`一句话 → 12 个动词之一 + N 个槽位 → 确认卡 → 落库`。

- **动词识别 = 12 分类问题** —— BERT 级别（100M–300M）就能做到 95%+
- **槽位抽取 = NER/正则** —— 你的规则引擎已经 **96% 动词 / 98.3% 槽位**
- **生成式 LLM 在这里是杀鸡用牛刀**，而且有个致命问题：**自回归生成 JSON 太慢**

### 2.2 速度账（这是最容易被忽略的）

| 环节 | 1.7B Q4 纯 CPU 实测估算 | 备注 |
|---|---|---|
| 生成完整 JSON（~80 token） | **3–5 秒** | 语音场景不可接受 |
| 只输出动词名（3–5 token） | **0.3–0.5 秒** | 可接受 |

参考你机器 A 的实测数据（16GB Q4_K_M，MoE 激活 3B，纯 CPU）：**9.4 t/s**。1.7B 密集模型在纯 CPU 上大概 15–25 t/s，但那也要看输出多少 token。

> ⚠️ **如果让 1.7B 吐完整 JSON，用户说完话要干等 3–5 秒才出确认卡。这是体验杀手，比准确率问题严重得多。**

### 2.3 推荐的三层架构（回答「能否按需加载」）

```
语音 → [ASR 常驻] → 文本
                      ↓
        L0  正则 + 个人用语表          ~0ms     命中率 ≈ 80–90%
                      ↓ 未命中
        L1  0.6B 分类（只输动词名）    ~0.3s    补到 ≈ 96%
                      ↓ 仍不确定
        L2  1.7B 生成兜底 / 云端 API   ~1–4s    补最后 4%
```

**关键决策**：
- L0 用你已有的规则引擎 + `PersonalLexeme`（用语表）—— 已经在做，零成本
- L1 用 **Qwen3-0.6B（400MB）**，只让它输出动词名，配合 GBNF 约束解码限制输出只能是 12 个动词之一 → 输出 3–5 token，快且不会胡说
- L2 的 1.7B **按需加载**（进程外，用完释放）或走云端。**不要常驻内存**

**结论**：要 1.7B 这个档，但它是「兜底件」不是「主引擎」。安装包里可以不带它。

- **首选 Qwen3 系列**：Apache 2.0 干净、中文强、GGUF/ONNX 生态最成熟、llama.cpp / Ollama 一键跑、社区量化版本最多

- **不要选**：GLM-Edge、MiniCPM（许可）；Fox-1.6B（昇腾专用）

## 四、Q3 · ASR 方案（你的核心需求）

### 4.1 先分清「流式」和「非流式」

| 类型 | 特征 | 适合 |
|---|---|---|
| **真流式** | 边说边出字 | 实时字幕、同传 |
| **非流式 + VAD 分段** | 检测到你说完停顿 → 整段识别 → 一次性出结果 | **语音指令、语音输入**（你的场景） |

> 对 ERP 语音输入，**VAD 分段更合适**：一句话完整识别，上下文完整，准确率高于流式；延迟只多一个「尾音检测」的时间（可配 200–400ms）。

### 4.2 ASR 方案对比

| 方案 | 体积 | 中文 CER | 流式 | 热词 | 许可 | 备注 |
|---|---|---|---|---|---|---|
| **sherpa-onnx + SenseVoice int8** ⭐ | **229MB** | ~7.1%（通用） | 非流式（配 VAD） | ⚠️ 需实测 | Apache 2.0 | **推荐**。含中英日韩粤，内置 ITN + 标点，非自回归快 |
| sherpa-onnx + SenseVoice 非量化 | 895MB | 同上 | 非流式 | 同上 | Apache 2.0 | 体积翻 4 倍，不值 |
| sherpa-onnx + streaming Zipformer int8 | **20.3MB** | 中 | **真流式** | ✅ 支持 | Apache 2.0 | 极低配/真流式需求 |
| sherpa-onnx + Paraformer | ~116MB | 较好 | 两种都有 | ✅ 支持 | Apache 2.0 | 平衡档 |
| sherpa-onnx + FireRedASR v2 | 待测 | 好，20+ 方言 | 两种 | 待测 | Apache 2.0 | 已集成，值得实测 |
| FunASR-Nano | 待测 | **4.17%**，热词 70.5%→88% | 待测 | **最强** | 待测 | 数据最好，但依赖 ModelScope，离线打包成熟度待验证 |
| Whisper-small (whisper.cpp) | ~500MB(Q5) | 中，中英混下降 | 非流式 | initial_prompt | MIT | 中文不如 SenseVoice，体积还大 |
| Qwen3-ASR | 大 | 近 SOTA，30 语 + 22 方言 | 自回归，**慢 7×** | 待测 | Apache 2.0 | 自回归，27 分钟音频 224s，不适合实时 |

### 4.3 为什么推荐 sherpa-onnx 而不是直接用 FunASR

**FunASR/SenseVoice 官方 Python 包内嵌 ModelScope SDK，即使模型已在本地，启动仍会尝试连接 modelscope.cn 校验**（GitHub Issues #2573/#1581/#1286，官方绕过方案实测不可靠）。对要离线分发的软件这是致命的。

sherpa-onnx 把模型转成纯 ONNX，指定本地文件路径，**永不联网**。额外好处：

- Apache 2.0，Kaldi 之父 Daniel Povey 团队（k2-fsa），GitHub 10.9k stars，持续更新（v1.12.29 / 2026-03）
- 12 种语言绑定，**Rust 可静态链接进二进制**（`cargo add sherpa-onnx --features static`）—— 对你的 Tauri/Electron 打包极友好
- 内置 Silero VAD、标点恢复、ITN、说话人识别、降噪
- 支持 NPU 加速（RKNN / QNN / 昇腾 / Axera）
- **纯 CPU 就是它的主场**，不需要 CUDA

### 4.4 ⚠️ 热词（hotword）是你这个场景的命门

公开实测（2600 条语音，1000 条含热词）：

| 模型 | 基础热词准确率 | 加热词后 |
|---|---|---|
| SenseVoice | **50.17%** | 76.12% |
| FunASR-Nano | 70.52% | **88.01%**（组合策略 88.49%） |
| GLM-ASR | 62.47% | 86.84% |

**SenseVoice 的热词基础准确率只有 50%** —— 意思是「张三」「A-100」「华东仓」这类专有名词，**一半会认错**。

对 ERP 来说，客户名和产品编码认错 = 下错单。所以：

1. **必须建热词表**：从你的 Customer / Product / Warehouse 表自动生成，每次打开软件时加载
2. **必须用同音字兜底**：「张三」的错误写法也要进表
3. 如果 SenseVoice 热词实测不达标，**换 FunASR-Nano 或 Paraformer**（热词支持更成熟）
4. 无论 ASR 多准，**确认卡不能省** —— 这是你架构里最正确的一个设计

### 4.5 体积 vs 准确率取舍

```
20MB   Zipformer流式 ── 极低配/真流式，专有名词基本靠猜
116MB  Paraformer   ── 平衡，热词支持成熟
229MB  SenseVoice   ── 中文最优，5语种，ITN+标点齐全   ← 推荐
895MB  SenseVoice   ── 非量化，收益极小
```

**229MB 是拐点**：往下省 200MB 换来的是专有名词准确率大幅下降，不划算；往上花 666MB 换不到明显提升。

## 五、Q4 · 最小体积组合方案

### 5.1 方案 A：极简版（推荐作为安装包本体）

| 组件 | 体积 | 内存占用 | 延迟 |
|---|---|---|---|
| sherpa-onnx 引擎（静态链接） | ~6MB | — | — |
| SenseVoice int8 ONNX | 229MB | ~400MB | — |
| Silero VAD | ~2MB | ~10MB | — |
| ITN + 标点（内置） | 0 | — | — |
| 规则引擎 + 个人用语表 | ~0 | ~0 | ~10ms |
| **合计** | **≈ 240MB** | **≈ 450MB 常驻** | **语音结束 → 出文本 ≈ 0.5–0.8s** |

**这个版本完全能用**：ASR + 规则 + 你的用语表，覆盖 80–90% 的日常说法。零 LLM 依赖，零显存需求。

### 5.2 方案 B：标准版（推荐目标形态）

| 组件 | 体积 | 内存 | 延迟 |
|---|---|---|---|
| 方案 A 全部 | 240MB | 450MB | 0.5–0.8s |
| + Qwen3-0.6B Q4（**可选下载**，只做动词分类） | +400MB | +600MB（按需） | +0.3s |
| **合计** | **≈ 640MB** | 常驻 450MB / 峰值 1.05GB | **≈ 0.8–1.1s** |

### 5.3 方案 C：完整版（1.7B 兜底，可选）

| 组件 | 体积 | 内存 | 延迟 |
|---|---|---|---|
| 方案 B 全部 | 640MB | — | 0.8–1.1s |
| + Qwen3-1.7B Q4 或 星火 X2.5-1.7B 4bit | +1.1GB | +1.5–2GB（**用完即释放**） | +1–4s（仅兜底时） |
| **合计** | **≈ 1.75GB** | 峰值 ~3GB | 兜底路径 2–5s |

### 5.4 打包策略（关键）

```
安装包本体（必装）   240MB   ← 开箱即用，无需下载任何模型
可选组件（首次使用时下载，或设置页手动触发）
  ├─ 0.6B 分类器      400MB
  └─ 1.7B 兜底模型    1.1GB
```

好处：
- 安装包 <250MB，分发/下载门槛低
- 低配机器可以永远不装 LLM，纯规则照样跑
- LLM 坏了/下载失败不影响主功能

### 5.5 延迟预算（语音输入全链路）

| 环节 | 耗时 | 说明 |
|---|---|---|
| VAD 尾音检测 | 200–400ms | 可调，调低易截断，调高觉迟钝 |
| SenseVoice 识别 5s 音频（CPU 4–8 线程） | 300–500ms | RTF ≈ 0.06–0.10 |
| ITN + 热词纠正 | <20ms | 数字「一百二十」→「120」 |
| 规则消解（命中时） | ~10ms | |
| **小计（L0 命中，80–90%）** | **≈ 0.55–0.95s** | ✅ |
| + 0.6B 分类（10–15%） | +0.3s | |
| **小计（L1）** | **≈ 0.9–1.3s** | ✅ |
| + 1.7B 兜底（<5%） | +1–4s | ⚠️ 只在疑难句出现 |

**优化空间**：VAD 尾音检测调到 200ms，SenseVoice 开 8 线程，L0 命中路径可压到 **0.5s 内**。

## 八、三个提醒

1. **ASR 错了比 LLM 错了更致命。** LLM 答错你能看出来，ASR 把「张三」听成「章三」你会直接落库。确认卡 + 数字二次确认不能省。
2. **别让 1.7B 吐完整 JSON。** 3–5 秒的等待会毁掉语音输入的体验。让它只做分类，槽位交给规则。
3. **星火 X2.5 是 9 天前才开源的**，官方数据无第三方验证。它的 90.3%/0.85s 是对口数据，值得测，但**别直接押注**，先用 Qwen3 把链路跑通再换。
