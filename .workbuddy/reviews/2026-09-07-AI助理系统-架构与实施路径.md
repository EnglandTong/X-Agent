## 零、方向校验（先对齐，再谈实现）

### 0.1 你的定位：80% 认同，缺两个器官

| 你的说法 | 校验 | 结论 |
|---|---|---|
| 大模型 = 大脑（推理决策） | ✅ | 但**它同时也是控制器**，见 0.2 |
| Agent = 手脚（执行动作） | ⚠️ | 分工对，**实现上不要单独写"Agent 编排引擎"**，见 0.2 |
| OCR/VLM = 眼睛 | ✅ | 但现阶段 ERP 场景只需 OCR，VLM 延后，见 3.4 |
| 语音 = 耳朵和嘴 | ✅ | 注意 ASR 错误是"不可见错误"，最危险 |

**缺的第一件：记忆（海马体）。**
没有记忆层，助理每次都从零认识你 —— 昨天说"老王就是张三"，今天它又问。
`Agent_ERP` 已有 `PersonalLexeme`（表 + 5 条路由 + 两个插入点），这就是记忆层的雏形，**直接升格为主干组件，不要重写**。

**缺的第二件：护栏（刹车）。**
ERP 落库是不可逆动作。没有"人在回路确认 + 权限 + 审计"，助理犯一次错你就再也不敢用。
护栏不是可选项，是**让"替人干活"这件事成立的前提**。

**修正后的六要素：**

```
耳（ASR） + 眼（OCR/VLM） + 脑（LLM） + 手（插件） + 记（Memory） + 闸（Guardrail）
```

其中「记」和「闸」是你原描述里没有、但决定项目生死的。

### 0.2 一条要顶回去的：别单独写 Agent 编排引擎

现代 agentic 实现里，**LLM 本身就是控制器**：你给它工具列表，它输出调用，你执行、把结果喂回去，循环。
"Agent = 手脚"这个比喻会诱导你去写一套独立的规划/调度引擎 —— **这是这类项目最常见的死法**（规划器 + 执行器 + 记忆管理器三件套，写到第 3 周还没跑通第一个任务）。

**建议：`Agent 层 = 一个 while 循环 + 工具注册表`。** 不超过 200 行。
复杂度应该长在"工具 manifest 写得好不好"，不是长在"编排引擎智不智能"。

### 0.3 痛点校验：方向对，归因要修

> 「大模型越来越强、部署成本动辄百万，但真实场景只用到极小一部分能力」

**对的部分**：能力与落地之间的适配层缺失 —— 这句是整件事的纲领，完全正确。

**要修的部分**：百万成本来自**私有化部署 + 自建推理集群 + 微调**，那是为"数据不出内网"付的合规溢价。你的场景根本不需要。

**实测测算（按你的使用强度）：**

| 假设 | 数值 |
|---|---|
| 每天指令数 | 100 条 |
| 需上云比例（其余走规则/本地） | 20% |
| 单次 token（system + 最小结构化上下文 + 输出） | ≈ 950 |
| 月 token 量 | ≈ 57 万 |
| 国产主流 API 单价 | 输入 ¥1–2/百万，输出 ¥8/百万 |
| **月成本** | **< ¥10** |
| 即便 100% 全走 GPT-4o 级 | ≈ ¥150/月 |

**结论：瓶颈从来不是模型钱，是"有多少能力真的被接进来了"。**
这句话应该写进项目 README 第一行。你真正要建的是**适配层（把模型能力接到具体任务上）**，不是省钱层。

## 一、整体分层架构

```
L1 交互层  Interface     —— 语音/文本/截图/快捷键 → 归一为一次「意图提交」
L2 编排层  Orchestrator  —— 路由 → 选插件 → 补全槽位 → 确认 → 执行 → 播报（核心循环）
L3 能力层  Plugin Reg.   —— 每个能力一份 manifest，三处消费
L4 模型层  Model Router  —— R0/R1/R2/R3 四档，按置信度分诊
L5 感知层  Perception    —— ASR（耳）· OCR/VLM（眼）· TTS（嘴）
L6 数据层  Memory        —— 个人用语 · 运行留痕 · 审计日志 · 配置

横切 A  护栏 Guardrail   —— 写操作必确认 · 权限 · 不可逆拦截 · 审计
横切 B  评测 Eval/Trace  —— 每次调用可回放 · 回归集 · 成本追踪
```

### 1.1 三个决定架构成败的设计点

**① 一份 manifest，三个消费者（核心发明，直接复用 Agent_ERP 的 x-agent）**

```
plugin.manifest.json  (JSON Schema + x-agent 扩展)
   ├─→ LLM tool definition   （function calling 的 parameters）
   ├─→ UI 确认卡              （Formily 直接渲染）
   └─→ CLI / HTTP API         （自动化测试与脚本调用）
```

这一条的价值：**加一个能力只写一份声明，UI 和模型同时得到它。**
Agent_ERP 已经用它跑了 12 个动词，是本项目唯一经过验证的核心资产 —— **升格为主干协议，不要新定第三套**。

**② 模型路由是成本与延迟的总闸（四档分诊）**

| 档 | 手段 | 体积 | 延迟 | 承担什么 |
|---|---|---|---|---|
| **R0** | 规则 / 正则 / 个人用语 / 已知映射 | 0 | < 1ms | 数字、日期、已记住的客户名与说法 |
| **R1** | 本地小模型分类（0.6B，只吐动词名） | ~400MB | 0.3–0.5s | 动词分类 |
| **R2** | 本地中模型（1.7–4B） | ~1.1GB | 1–3s | 复杂槽位抽取、歧义消解 |
| **R3** | 云端大模型 | 0 | 0.5–2s | 长上下文、多模态、R2 仍低置信 |

铁律：**R3 只传最小结构化上下文，绝不传整库。**
分诊顺序 R0 → R1 → R2 → R3，命中即停。

**③ 每次任务是一个 Run，六态落库**

```
received → interpreted → resolving → awaiting_confirm → executing → done | failed | rejected
```

落库的原因：它是 Eval、审计、错误回放的**唯一数据源**。
Agent_ERP 的 canvas "格子提交即冻结" 已经是这个模型的实例，直接沿用。

### 1.2 进程模型：先同进程，后隔离

阶段 1–3 全部同进程（Node/TS 或 Python 二选一），**不要一开始就上 gRPC / 子进程沙箱**。
插件安全性靠 manifest 声明 `risk` 等级 + 护栏确认，不靠进程隔离。等到 S5 接第三方插件再谈沙箱。

## 二、最小可用闭环（一个场景跑通全链路）

### 2.1 三个候选

| 候选 | 场景 | 优势 | 风险 |
|---|---|---|---|
| A | **语音开单**：一句话 → 确认 → 落库 → 播报 | 已有 90% 资产，一周可跑通；同时验证 耳→脑→手→闸 | 与 Agent_ERP 已有功能重叠 |
| B | 单据截图 → 结构化录入 → 报告草稿 | 真实痛点最强 | 触碰公司数据合规红线 R1 |
| C | 个人知识库问答 | 最安全、最高杠杆 | 不能验证"替人完成重复操作" |

### 2.2 推荐：A 的变体 —— 在独立 Assistant Core 里跑 order.create

**不是**在 Agent_ERP 里加功能，而是：新建 Assistant Core，把 Agent_ERP 的 `order.create` 作为**第一个插件**接进来。
这样既验证了主干，又证明了主干能复用已有资产 —— 这是 S3 接第二个应用的前提。

### 2.3 闭环六步

| 步 | 动作 | 技术 |
|---|---|---|
| 1 | 按住说话 → 转写 | sherpa-onnx + SenseVoice int8（229MB），**注入热词** |
| 2 | 文本 → 意图路由 | R0 个人用语/规则 → R1 本地分类 → R3 云端 |
| 3 | 命中插件 + 槽位消解 | 客户/产品/数量 → `resolve` |
| 4 | 生成确认卡 + 语音复述 | Formily 渲染 manifest + TTS："给张三开 100 个 A-100，确认吗" |
| 5 | 人确认 → 执行 → 落库 | 语音「是」或点击；写操作必须过这步 |
| 6 | 结果播报 + 记忆更新 | 若用户改过预填 → 提议记住；同意则入 PersonalLexeme |

### 2.4 第一阶段明确不做

OCR / VLM · 多插件（只 1 个）· 本地模型（只用云端 + 规则）· mini apps 并入 · 移动端 · 云端同步 · 多用户权限

## 三、能力选型（轻量、成本可控、可闭源分发）

### 3.1 选型表

| 能力 | 方案 | 体积 | 延迟 | 许可 | 闭源分发 |
|---|---|---|---|---|---|
| **ASR** | sherpa-onnx + SenseVoice int8 | 229MB | RTF≈0.1 | Apache-2.0 | ✅ |
| ASR 轻量备选 | sherpa-onnx + Paraformer 流式 | 116MB | 更低 | Apache-2.0 | ✅ |
| **TTS（S1）** | Windows SAPI 系统语音 | **0MB** | < 50ms | 系统自带 | ✅ |
| TTS（S3） | sherpa-onnx Matcha-ZH + vocos | 123MB | RTF≈0.1 | Apache-2.0 | ✅ |
| TTS 更小备选 | Piper ZH int8 | ~40–60MB | 快 | MIT/Apache | ✅ |
| **本地分类（R1）** | Qwen3-0.6B Q4 | ~400MB | 0.3–0.5s（仅动词） | Apache-2.0 | ✅ |
| 本地兜底（R2） | Qwen3-1.7B Q4 / 星火 X2.5-1.7B | ~1.1GB | 1–3s | Apache-2.0 | ✅ |
| 云端（R3） | DeepSeek / Doubao / 火山 Ark | 0 | 0.5–2s | 商用 API | ✅（审条款） |
| **OCR（S3）** | RapidOCR（PP-OCRv4 mobile） | ~15MB | 50–200ms | Apache-2.0 | ✅ |
| VLM | 暂缓 | — | — | — | ❌ 见 3.4 |
| 记忆 | SQLite + PersonalLexeme | 0（已有） | < 5ms | — | ✅ |

### 3.2 ⚠️ 许可红线（决定能否随商业软件闭源分发）

- ✅ **Apache-2.0 / MIT**：Qwen3、星火 X2.5、sherpa-onnx 全系、RapidOCR —— 只需在 About 页附带 LICENSE 文本，**无署名义务**。
- ❌ **GLM-Edge**（要求 UI 显著显示 "Built with GLM-Edge"）
- ❌ **MiniCPM / MiniCPM-V**（要求显著署名，且端侧超 5000 台或 DAU 100 万需单独申请；权重还需登记）

**这两家在本项目直接出局。** 选型时只看 Apache-2.0 / MIT，省得做完才发现分发不了。

### 3.3 体积组合

| 阶段 | 组成 | 总体积 |
|---|---|---|
| S1 | ASR 229MB + 系统 TTS 0 + 规则/云端 | **≈ 230MB** |
| S2 | + 本地 0.6B 400MB | ≈ 630MB |
| S3 | + OCR 15MB + 离线 TTS 123MB | ≈ 770MB |

**打包策略**：安装包只放 S1 的 230MB。本地模型与 OCR 作为**可选组件首次使用时下载** —— 低配机器永远不装也能完整使用。

### 3.4 关于多模态：先 OCR，后 VLM

你提到"LLM 最好有多模态手法"，方向认同，节奏建议调整：
- **现在 ERP 场景只需要 OCR**（单据、名片、产品编码），RapidOCR 15MB、毫秒级，覆盖 90% 需求。
- **VLM 的许可当前是硬伤**：MiniCPM-V 代码 Apache-2.0 但**权重要登记 + 宣传限制**，与闭源分发冲突。
- 建议：**接口先留，实现延后**。VLM 等到"理解图表/场景"这类高阶需求出现，届时按需下载或走云端。

### 3.5 两个已知的 ASR 坑（必须先验）

1. **FunASR / SenseVoice 官方 Python 包内嵌 ModelScope SDK，离线也会尝试联网校验**。要打包分发必须走 sherpa-onnx 的 ONNX 版本。
2. **SenseVoice 热词基础准确率仅 50.17%**。"张三""A-100""华东仓"这类专有名词一半会认错（对比 FunASR-Nano 加热词后 88.49%）。**必须从 Customer/Product 表自动生成热词表 + 同音字兜底**，不达标就换 Paraformer。
   → 这条优先级**高于选模型**，S1 第一件事就该验。

### 「抽 core/」的精确定义：目录先分家，代码先不动

```
Agent_ERP/app/src/
  core/                    ← S0 新建，只放协议与类型，不放实现
    00_MANIFEST.md            协议一页纸
    manifest.schema.json      JSON Schema
    run.ts                    Run 六态（纯类型，无逻辑）
    registry.ts               插件注册表（只登记，不改 verbs 执行代码）
  server/verbs/             ← 一行不动，作为「第一批插件」
```

**铁律：`core/` 不得 `import` `server/verbs/`。** 单向依赖。
verbs 被"登记"进 registry 靠 manifest 声明，不是代码引用 —— 这条守住了，将来 `git mv core/ ../AssistantCore` 就是一次目录移动，零重写。

**S0 交付物**：目录 + 一页纸 + `manifest.schema.json` + `order.create` 改写样例。
**零行现有代码改动。**
