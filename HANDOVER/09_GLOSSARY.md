# 09 · 术语表 & Owner 协作偏好

---

## 一、术语表

| 术语 | 含义 |
|---|---|
| **动词（verb）** | 系统能做的业务动作（`order.create`）。不是 REST 资源 |
| **槽位（slot）** | 模型要抽的信息单元（`customer`、`quantity`），由 `x-agent.extract` 声明 |
| **字段（field）** | 表单/数据库的字段名（`customerId`）。**槽位名 ≠ 字段名**，这是最常踩的坑 |
| **消解（resolution）** | 把「原话片段」变成「落库值」的确定性转换（张三 → customerId） |
| **推断（inferFrom）** | 用户没说，系统按主数据/历史推出来（**必须高亮 + 低置信度**） |
| **格子 / Panel** | 画布上的一格 = 一条不可变审计记录（原话 / 抽取 / 落库 / 结果） |
| **关联键（correlationId）** | 界面级：`ORD:{单号}` / `CUS:{客户ID}`，把同一对象的操作串起来 |
| **变更单** | 已确认订单要改 → **另开新单**，不是改原单 |
| **originNo** | 新单指向原单（业务级串联） |
| **supersededByNo** | 原单指向新单（业务级串联） |
| **chainId** | 变更链根单号，整链共享，用于一次查全 |
| **修订** | 草稿单的原地修改（还没生效，可以改） |
| **引擎（engine）** | `rules` = 规则抽取；`llm` = 模型抽取。会显示在界面上 |
| **x-agent 协议** | Schema 里的扩展段，同时告诉 UI 和模型「这个字段怎么来」 |
| **Tool Schema** | 同一份 Schema 编译给模型的工具定义 |

## 二、Owner 协作偏好（照着做会很顺）

| 偏好 | 说明 |
|---|---|
| **输出格式** | Markdown + 表格 + emoji 状态标记 + P0-P4 优先级 |
| **AI 回复结构** | 他喜欢「AI 理解 / 关键缺口 / 下一问 / 暂不推荐」四段式 |
| **文档级别** | 要「操作规程级别」的正式文档，胜过对话式解释 |
| **严格范围** | **禁止顺手优化、投机性重构、合并工单**。范围漂移需 Owner 书面确认 |
| **审计风格** | 表格 + 严重度标签（P0/P1/P2）+ 关键证据引用 + **逐项复验状态列** |
| **输入特点** | 语音输入为主 → 句子碎片化、可能不完整 → 要结合上下文推断语义，不确定就问 |
| **会纠正你** | 他不接受「差不多对」。语义错了会明确指出，被纠正后要真正改到根上 |
| **输出被截断** | 会说「Resume」，接着往下写即可 |
| **批量任务** | 习惯一次性提多个关联任务，期望批量完成 |

## 三、给接手 AI 的行为准则

1. **先读再动**：读完 00-04 再写代码
2. **不确定就问**：尤其「是不是要改已有数据」这类不可逆操作
3. **不要顺手优化**：看到 `tsc` 有 10 处类型错误，不要自作主张去清 —— 先问
4. **改动词/改 Schema 前**确认范围，加动词要 Owner 点头
5. **每次阶段成果**主动导出 zip + bundle（这是他的痛点）
6. **模型相关改动**必须保留「失败回落规则引擎」这条保命路径
7. **不要动** `.env.local`、不要把 Key 写进任何文件或对话
