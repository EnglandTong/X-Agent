# 01 · 整体思路：为什么是这个形态

---

## 一、命题

> **ERP 不该是人去适应表单，而是系统去理解人。**

Owner 有 20 年独立开发经验与抽样质检背景，日常看到的是：真正的业务人员（尤其是一边操作一边说话的场景）
根本受不了「找菜单 → 切Tab → 填 20 个字段 → 保存 → 发现填错 → 再改」这条链路。

于是有了这个项目：**用一句话驱动业务动作，用不可变的格子记录每一次动作。**

---

## 二、四条设计信条

### 信条 1 · 动词驱动，不是资源驱动

系统里**没有** `/api/orders` 这种 CRUD 资源路由。有的只有「动词」：

```
order.create   建一张销售订单
order.confirm  确认订单（草稿 → 已确认）
order.query    查询订单
```

为什么：**「能做什么」由领域语言表达，而不是由数据库表表达。**
加一个能力 = 加一个动词 + 一份 Schema，不用开新路由、不用改前端。
动词清单本身就是给模型的工具定义（自省接口 `GET /api/verbs`）。

### 信条 2 · 表单按需生成（一份 Schema，两个消费者）

这是整个架构的地基：

```
                    ┌──────────────────────────┐
                    │  order.create.json       │
                    │  （Formily Schema）       │
                    │  + x-agent 扩展协议       │
                    └────────────┬─────────────┘
                                 │
              ┌──────────────────┴──────────────────┐
              ▼                                     ▼
      【消费者 A：UI】                      【消费者 B：模型】
      Formily 渲染成人看的                  compile.ts 编译成
      确认卡片（下拉框、日期器）             Tool Schema（工具定义）
```

**表单不是写死的前端页面**，它是 Schema 的渲染结果。
加一个字段 = 改一行 JSON，UI 和模型同时拿到它。

### 信条 3 · 记录不可变，改动另开新单

界面上的每一格（Panel）提交即冻结。要「改」，有且只有两种合法方式：

| 原单状态 | 动作 | 结果 |
|---|---|---|
| 草稿 `DRAFT` | **修订** | 原地更新同一张单，另起一格记录这次修订 |
| 已确认 / 已出货 | **变更** | **另开一张新单号**，原单冻结，两单业务字段双向串联 |

这不是技术洁癖，是**真实 ERP 的变更单语义**（详见 `03_VERBS.md`）。

### 信条 4 · 模型只做「听写」，不做「理解」

```
用户："给张三来120个A-100，下周三要"
        ↓ 模型（只输出原话片段）
{ verb:"order.create", slots:{ customer:"张三", product:"A-100",
                               quantity:"120", delivery_date:"下周三" } }
        ↓ 消解器（确定性代码）
{ customerId:"cmt…（张三·C001）", productId:"…（A-100 标准件）",
  qty:120, deliveryDate:"2026-09-09" }
```

模型**不背数据库主键**（1.7B 背不住）、**不算日期**（会算错）、**不转中文数字**（会转错）。
这些全交给 `resolve.ts` 的确定性代码，模型只剩「听」—— 这正是小模型能胜任的原因，
也让同一句话每次结果**可复现**。

## 三、交互形态：画布 REPL

用户选的是**完整画布模式**（A 方案）：

- 顶部：当前业务对象（跨格子共享上下文）
- 中部：格子列表，从上往下「Print」，版式固定、不追求漂亮、**适合数据抓取**
- 底部：永远在底部的命令输入框（像 CLI/REPL）

版式固定是刻意的 —— Owner 的原话是「适合生产与数据抓取」。
意味着：**不要为了好看引入自由布局、拖拽、动画**。固定格式 > 视觉花哨。

---

## 四、明确不做（范围外）

| 不做 | 原因 |
|---|---|
| 采购、生产、财务、人事 | 范围锁定「销售订单 → 出货」一条线 |
| 主数据维护界面（客户/产品增删改） | PoC 用种子数据即可 |
| 权限、多租户、登录 | 单用户验证范式 |
| 漂亮的可视化大屏 | 反目标：要的是固定版式、可抓取 |
| 复用到 BW_ERP 数据库 | **数据完全独立**，Greenfield，仅参考其格式与流程 |

---

## 五、它在 Owner 三条业务主线里的位置

Owner 并行三条线：① 小说内容 ② 量化投资工具 ③ **小软件/小工具开发（本项目）**。
第三条的关键成功因素他自己定过：**跑得快、量大、易被发现**。

所以对这个项目的隐含要求是：**PoC 要快速验证范式是否成立**，
不要在第 3 个动词上打磨三个月。验证通过 → 铺量；验证不通 → 及早知道。
