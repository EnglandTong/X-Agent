## 二、★ 修改语义的三次演进（最关键的纠正）

这是 Owner **两次纠正**才定下来的，务必理解清楚。

### 第一版（我理解错了）：原地修改
我最初做成「格子提交后可以原地编辑」。
**Owner 纠正 1**：

> 「每一个都只是唯独提交了不能改。要改是重新新开一个个表单……
> 在前一个记录跟后一个记录增加一个关联。词针里边的关键词吧。」

我据此改成：Panel 级 `correlationId` + 词典实体关键词。

### 第二版（还是没完全对）：界面级关联
Owner 又纠正（这条是分水岭）：

> 「我说的关键词是在两件单单子收过来的时候，前一段跟后一站有一些关键的信息去串联那个。
> 两个单子之前说第一个单子，如果提交了，就已经确认不能改了。然后面再改的时候，就是新的单子啊。」

**→ 定稿语义**：

1. 关键词不是界面父子关系，是**两张独立订单之间的业务关键字段串联**
2. 已确认的订单**不能改**，再改 = **另开一张新单号**
3. 两单用 `originNo` / `supersededByNo` / `chainId` **双向互指**
4. 草稿单可以原地「修订」（因为它还没生效）

这就是真实 ERP 的**变更单**模式。详见 `03_VERBS.md`。

> **教训**：Owner 说「关联」时，先问清楚是**界面级**还是**业务级**。
> 他关心的是业务语义，不是 UI 结构。

### 关于 DeepSeek V4 Flash 的 401

Owner 此前在别的工具上遇到过 `deepseek-v4-flash` 返回 401。
本项目的连通性测试会**返回服务端原始错误**，实测假 Key 的返回是：

```
HTTP 401 · 鉴权失败（key 无效 / 无该模型权限 / endpoint 不匹配）
detail: {"error":{"code":"AuthenticationError",
         "message":"The API key format is incorrect...","type":"Unauthorized"}}
```

排查顺序：**Key 格式 → 该 Key 是否开通该模型 → endpoint 与模型名是否匹配**。
（火山方舟的模型名也可能是 `ep-xxx` 接入点形式，设置面板允许手填。）

> 骨干的"躯干"= Agent Harness：不生产智能，负责让脑袋的决策**持续、可控、可恢复地**传到四肢（工具/应用）。

### 感官清单（开放枚举，加官不改协议）

| modality | 辨认器 | 当前状态 |
|---|---|---|
| `text` | 无（原生） | ✅ 键盘 / 输入法 —— **已有，最易被忽略的一官** |
| `audio` | ASR | 🟡 Web Speech 占位 → T2 SenseVoice int8（229MB，未开始） |
| `image` | OCR（远期 VLM） | 🔴 远期 |
| `touch` | 力/触觉传感 + 设备控制 | 🔴 远期（机器人 / 自动驾驶） |
| `thermal` / `smell` / … | 各自传感器 | 🔴 远期，仅预留 |

**关键原则**：所有感官在协议里产出同一种东西 —— **Observation（观测）**：

```jsonc
{ "modality": "audio", "source": "mic-01", "at": "ISO8601",
  "payload": "辨认后的结构化结果", "confidence": 0.87, "raw": "原始信号引用" }
```

加一个新感官 = 加一种 `modality` + 一个辨认器，**不动协议结构**。
三层拆分：**采集**（换硬件才改）→ **辨认**（换辨认器才改）→ **决策**（永远不改）。
控制是感知的镜像：Observation（进）· Action（出，= 12 动词）· Run（中间状态）。
（现行同构先例：x-agent 的 `resolution` 字段 —— 加消解策略不动架构。）

## 十二、记忆的写入策略：候选区 + 跨天阈值（2026-09-07 Owner 定）

**问题**：一次点击就把说法写进个人用语表，会把口误 / ASR 噪声当习惯（如「老呃张老」）。
**Owner 的原话**：「如果某一次他说『老张』或『老呃张老』，那可能只是不小心说的，不一定是一个标准的需求。」

### 三层结构

```
① 观察  candidate   说法出现 → 记一笔证据（不参与消解，绝不自动生效）
② 证据  co-occur    与目标的共现次数 + 跨天数
③ 升格  active      达到阈值 → 转正式记忆卡，画布提示「我注意到你常说 X，要记住吗？」
```

### 升格阈值（三选一，Owner 选 B）

| 方案 | 规则 | 结论 |
|---|---|---|
| A · 计数 | 同一说法指向同一目标 ≥ 3 次 | ❌ 一天内连说 3 次也会升格 |
| **B · 跨天** ⭐ | **≥ 2 次 且 跨 ≥ 2 天** | ✅ **已采纳** —— 最能过滤"今天随口一说" |
| C · 仅显式 | 只有点「记住」才生效 | ❌ 等于现状，只是加提示 |

**为什么 B 能过滤噪声**：噪声的本质是**不稳定**（每次长得都不一样），永远累积不到跨天计数；
真别名的本质是**稳定重复**，自然会跨天累积。阈值即噪声过滤器。

### 节点网络从哪来（不新建图存储）

`Panel` 里已经躺着三样东西，网络是**派生**出来的，不是新建的：

| 图的部件 | 现有数据 |
|---|---|
| 节点 | `Panel.entities` = `[{type,value,label}]`（客户 / 产品 / 仓库 / 单号） |
| 共现边 | 同一 Panel 的 entities 两两相连 |
| 同对象边 | 相同 `Panel.correlationId` |
| 时序边 | 同 session 内按 `createdAt` 相邻 |
| 映射边 | `PersonalLexeme`：说法 → 目标 |

### 明确不做

- ⛔ 引入图数据库（Neo4j 等）—— 红线：不 clone 整包框架；SQLite 一张共现表足够
- ⛔ 接入 Obsidian / 建 vault —— 那是另一个应用，会让两个事实源打架
- ⛔ 向量检索 —— 决策 #13 已否决；这里要的是**计数**，不是相似度
